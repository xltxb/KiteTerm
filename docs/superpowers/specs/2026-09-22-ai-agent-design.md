# AI 分步执行(Agent)设计

日期:2026-09-22
状态:已确认
来源:用户提供参考截图(另一款 AI 终端),要求把 AI 能力从「单次生成一条命令」升级为
      「带确认的分步执行循环」——AI 提出命令 → 执行 → 读到输出 → 据此决定下一步,
      失败时能自我修正(如 `sed` 报 Permission denied 后改用 `sudo`)。

## 目标

给终端 AI 加一个有状态的执行循环:围绕一个目标连续推进,每步收集输出并分析,
只读命令自动执行、写操作停下来等用户批准,失败时允许有限次自我修正。

## 非目标

- 不做全自动 agent。写操作永远需要人点批准,这条不可配置。
- 不改现有三种 AI 模式(chat / explain / command / summary)的行为。
- 不做跨主机编排。一个任务绑定一个会话,不会替用户在多台机器间跳。
- 不追求截图里「确认块内联在终端输出之间」的形态 —— 技术上做不到,见「可行性约束」。

## 已定决策

| 决策 | 取值 | 理由 |
|---|---|---|
| 执行权 | 只读自动、写操作批准 | 用户选定 |
| 只读判定 | 本地白名单+语法检查 **且** AI 声明,两者 AND | 用户选定。本地那层是安全边界,AI 那票只是更保守的阀 |
| 执行通道 | 注入当前终端会话 | 用户选定。保住 cwd、环境变量与可见痕迹 |
| 失败处理 | 连续失败 2 次即停 | 用户选定。够覆盖「换 sudo 重试」,又不会无限折腾 |
| 输出边界 | APC 隐形哨兵 | 复用项目已有手法(见下) |
| UI 落点 | 「AI 助手」tab 内分「对话 / 任务」两模式 | 右栏 284px,加第四个 tab 会把中文标签挤坏 |
| 功能开关 | 新增 `aiAgent` | 能执行命令是性质不同的能力,管理员要能单独禁掉 |

## 可行性约束

参考截图里「Agreed 确认块内联在命令输出之间」的形态,**在 KiteTerm 里实现不了**。
那款工具的终端应是 DOM 渲染,可在输出流中间插入交互组件;KiteTerm 用 xterm.js +
WebGL canvas,终端内容是画上去的像素,无法在其中嵌入 React 按钮。xterm 的
decorations API 只能做行级标记(小图标、高亮),撑不起带按钮的确认块。

因此「批准」交互必须在终端之外 —— 右栏面板。终端里仍能看到命令与输出(因为是注入执行)。

## 一、执行循环

### 单步的形状

注入终端的不是裸命令,而是命令 + 隐形哨兵:

```
<命令>; printf '\033_KTEND:%s\033\\' "$?"
```

命令与输出照常显示,退出码包在 APC 序列(`ESC _ … ESC \`)里 —— **xterm.js 会整段忽略,
用户看不见**,Rust 侧从终端流里抓。一次拿到三样东西:输出的起止边界、退出码、
不被污染的终端显示。

这不是新发明:`ssh.rs` 的 `DROP_RZ_COMMAND` 早已用同一手法探测远端 cwd,连坑都踩过了
——用 `\033` 八进制而非裸 ESC 字节,shell 回显命令行时才不会夹带控制字符。

### 一步的生命周期

```
AI 提出命令
  → 本地判定(白名单 + 语法检查)
  → 本地判定为只读 且 AI 也声明只读 → 自动注入
    否则 → 挂起,等用户在右栏点批准
  → 注入终端,等哨兵
  → 抓到 KTEND:<code> → 截取这一步的输出
  → 连同退出码回灌给 AI
  → AI 返回:分析 + 下一步 / 完成
```

### 循环边界

三道闸,任一触发即把控制权交回用户:

| 闸 | 阈值 | 理由 |
|---|---|---|
| 连续失败 | 2 次 | `sed` 失败改 `sudo` 是第 1 次自改;再失败说明方向错了 |
| 总步数 | 12 | 防死循环烧 token |
| 等哨兵超时 | 30 秒 | 命令挂起(等输入等)时不能无限等 |

用户可随时点「停止」中断循环。

### 状态

新建 `stores/agent.ts`,与 `ai.ts` 分开:`ai.ts` 是无状态的请求-响应,agent 是有状态的
长流程(当前任务、步骤列表、每步的命令/判定/输出/退出码、循环计数)。

**任务绑定会话**。切标签页不中断任务,但注入只发给它自己那个会话 —— 否则用户切到另一台
主机后,AI 的下一条命令会跑到错的机器上。

### 分析与总结

AI 每次响应同时给出分析与决策,不额外增加调用:

```json
{
  "analysis": "sshd_config 里 X11Forwarding 那行是注释掉的,当前走编译默认值",
  "next": {
    "intent": "取消注释并改成 yes",
    "command": "sudo sed -i 's/^#*X11Forwarding.*/X11Forwarding yes/' /etc/ssh/sshd_config",
    "readonly": false
  },
  "done": false
}
```

结束时给 `summary`,右栏顶部出总结卡(做了什么、结果如何、遗留注意事项),**可一键复制成
文本** —— 运维改完线上配置往往要往群里贴说明。

## 二、安全

核心原则:**本地判定不信任 AI**。

### 判定有两个维度

自动执行要求**同时满足**:不改变状态 **且** 会自行终止。后者常被忽略:

| 命令 | 只读 | 问题 |
|---|---|---|
| `tail -f` / `journalctl -f` | 是 | 永不返回,哨兵等不到 |
| `top`(无 `-b -n`) | 是 | 交互式全屏,搅乱终端 |
| `less` / `more` | 是 | 等用户按 q |
| `ping`(无 `-c`) | 是 | 一直跑 |

### 本地判定流程(Rust 侧)

```
1. 含以下结构任一 → 判为「需批准」:
     重定向 > >> <     管道 |     串联 ; && || &     换行
     命令替换 $(...) `...`        进程替换 <(...) >(...)
2. 此时必为单一命令,取第一个 token 作可执行名
3. 该名字必须在只读白名单内
4. 命中「需检查参数」的命令,再过参数规则
5. 全过 → 只读;任一不过 → 需批准
```

第 1 步即拦掉绝大多数逃逸:`cat x > /etc/passwd`、`ls; rm -rf /`、`grep foo | sh`、
`echo $(rm -rf x)`。注意是**判为需批准**而非拒绝 —— 用户仍可批准执行。

只读白名单(首版。**宁可误拦不可误放** —— 遗漏只是多问一次,放错是在生产机上执行未授权写操作):

| 类别 | 命令 |
|---|---|
| 文件查看 | `ls` `cat` `head` `tail` `stat` `file` `wc` `readlink` `realpath` |
| 搜索 | `grep` `egrep` `fgrep` `find` `which` `whereis` |
| 系统信息 | `pwd` `whoami` `id` `hostname` `uname` `uptime` `date` `env` `printenv` |
| 进程 | `ps` `pgrep` `top` |
| 磁盘 | `df` `du` `lsblk` `mount`(无参数时) |
| 网络 | `ip` `ifconfig` `netstat` `ss` `ping` `dig` `nslookup` |
| 包管理 | `dpkg -l` `rpm -qa` `apt list`(仅这些只读子命令) |
| 服务 | `systemctl` `journalctl`(子命令受限,见下表) |
| 版本控制 | `git`(子命令受限,见下表) |
| 其他 | `echo` `sha256sum` `md5sum` `diff` `sort` `uniq` |

参数规则(白名单命令里藏写操作或挂起的情形):

| 命令 | 规则 |
|---|---|
| `find` | 出现 `-exec` / `-execdir` / `-delete` / `-fls` / `-fprint` → 需批准 |
| `tail` / `head` | 出现 `-f` / `--follow` → 需批准 |
| `ping` | 必须有 `-c` |
| `top` | 必须同时有 `-b` 与 `-n` |
| `journalctl` | 出现 `-f` / `--follow` → 需批准 |
| `systemctl` | 子命令限 `status` / `is-active` / `is-enabled` / `list-units` / `show` |
| `git` | 子命令限 `status` / `log` / `diff` / `show` / `branch` |

`less` / `more` / `vi` / `vim` / `nano` **不进白名单** —— 本质交互式,没有安全用法。

### prompt injection

攻击面真实存在:AI 读的是命令输出,而输出可被攻击者控制(往日志里写一段话等运维 `cat`)。
四层防护,**最后两层才是真正管用的**:

1. **结构隔离** —— 输出包在明确的数据块里,system prompt 声明块内是数据非指令。挡普通情况。
2. **输出截断** —— 单步回灌上限 4KB,超长取头尾各 2KB 并标注省略。省 token 也缩小注入面。
3. **本地判定是最后防线** —— injection 能操纵 AI 说什么,操纵不了白名单。`curl | sh` 在
   第 1 步就因管道被判为需批准。
4. **写操作必须人工批准** —— 批准时用户看到的是**命令原文**,不是 AI 的描述。

补充:AI 的 `analysis` 本身可能被操纵(诱导用户点批准),故 UI 须区分「AI 说的」与
「机器记的」,见第三节。

### 破坏性命令

复用现有机制(`AiCommandBar` 已对删除/重启/强制覆盖类命令出警告):命中时批准按钮变红,
要求**点两次**确认。

### 测试

判定逻辑是纯函数,是安全边界,必须测透,按 TDD 先写逃逸用例:

- 每条逃逸形态各一例:重定向、管道、串联、命令替换、进程替换、换行
- 每条参数规则各一例:`find -delete`、`tail -f`、`ping` 无 `-c`、`systemctl restart`
- 白名单正常形态应判只读:`ls -la /etc`、`systemctl status sshd`
- 边界:空命令、纯空白、超长命令、非 ASCII

## 三、UI 与交互

### 落点

右栏 284px,三个 tab 各约 84px 刚好放下「快捷片段」;加到四个只剩 66px,中文标签会挤。
故 agent 放进现有「AI 助手」tab,用 `Segmented`(项目已有该原语)切「对话 / 任务」。

`AiDock` 拆为 `AiChatPane` + `AiAgentPane`,`AiDock` 变成管模式切换的壳 —— 顺带把当前
那个近 4KB 的单文件拆小。

### 发起任务

「任务」模式顶部:输入框 + 「开始」按钮,**目标主机固定显示**(取自当前会话)。这是防呆:
任务绑定会话,用户要随时看得见它跑在哪台机器上。切标签页时面板显示该会话自己的任务。

`AiFab` 加入口:选中一段输出 → 「让 AI 处理这个」→ 带上下文进入任务模式。

### 步骤卡片的五个状态

| 状态 | 表现 |
|---|---|
| 待批准 | 命令框 + `批准执行` / `跳过这步`。破坏性命令时按钮变红且要点两次 |
| 执行中 | 命令框 + 指示器 + 已用秒数(让 30 秒超时可见) |
| 成功 | 退出码 0 徽章 + 输出(折叠)+ AI 解读 |
| 失败 | 非零退出码徽章(红)+ 输出 + AI 解读。触发自改时下一张卡标「第 2 次尝试」 |
| 跳过 | 灰掉,保留命令原文备查 |

自动执行的只读命令不停下等待,直接从「执行中」到「成功/失败」。

### 「AI 说的」与「机器记的」

```
┌──────────────────────────────────┐
│ ✦ 取消注释并改成 yes              │ ← AI 说的(✦ 标记,正文字体)
│ ┌──────────────────────────────┐ │
│ │ sudo sed -i 's/.../' /etc/...│ │ ← 机器记的(等宽,框起来)
│ └──────────────────────────────┘ │
│ [写操作·待批准]                   │
│ ─────────────────                │
│ 退出码 0 · 输出 3 行  ▸展开       │ ← 机器记的
│ ✦ 配置已写入,下一步需要重启服务   │ ← AI 说的
└──────────────────────────────────┘
```

批准时用户看的永远是命令原文。

### 停止

面板顶部常驻「停止」(任务进行中才出现),点击立刻中断循环、不再注入新命令。

**已注入的命令停不掉**,它在远端跑着。UI 文案须如实说明,并提示用 Ctrl-C。不做自动补发
Ctrl-C —— 会误伤。

### 功能开关

新增 `aiAgent`。现有三个 AI 开关管的都是「AI 生成文本给你看」,agent 能执行命令,性质不同;
企业环境可能允许前三者而禁止它。不加的话管理员只能用 `aiCommand` 一刀切,粒度太粗。

代价:`server/` 开关注册表、`server-worker/` 同一份实现、客户端 `features.ts` 与
`types.ts` 都要登记,开关总数 11 → 12。改动机械但点位多。

## 风险与遗留

- **哨兵可能被用户的 shell 配置干扰。** 若用户 `PROMPT_COMMAND` 或 `precmd` 里有输出,
  可能落在哨兵与命令输出之间。实现时需以哨兵为准切分,不假设输出紧邻命令。
- **注入执行会把命令写进 shell 历史。** 与用户手敲无异,但 AI 高频执行会稀释历史。
  本次不处理,如需可后续加 `HISTCONTROL=ignorespace` + 前置空格。
- **只读白名单必然不完整。** 新命令、非 GNU 工具集(BSD/busybox)的参数差异都会让判定
  偏保守(多问一次)。这是有意的:宁可误拦,不可误放。
- **本设计未解决终端卡顿问题。** agent 会显著增加终端输出量,若卡顿根因未除(见另案),
  体验会被放大。建议先定位卡顿再上 agent。
